# Архитектура KROT zapret

## Границы процессов

`KROT.exe` работает с обычными пользовательскими правами. Он отвечает за интерфейс, локальные настройки, журнал и команды управления.

`KROT.Service.exe` работает как Windows Service от `LocalSystem`. Только служба может запускать и останавливать runtime-компоненты. GUI связывается со службой через версионированный Named Pipe, отдельный для SID активного пользователя. ACL разрешает доступ этому пользователю, локальным администраторам и `LocalSystem`.

Служба учитывает PID, время запуска, SHA-256 и маркер владения. Глобальное завершение процессов по имени запрещено.

## Runtime

Runtime разделён на две роли:

- `main` — TCP/TLS-каналы выбранных сервисов на Zapret 1;
- `voice` — адаптивный UDP-процесс Zapret 2: YouTube QUIC, Discord Voice и STUN.

Перезапуск `voice` не затрагивает `main`. Внутри UDP-процесса обёртка KROT над оркестратором `circular` отдельно ведёт YouTube QUIC и Discord Voice: при обнаружении нового подходящего UDP-потока она сообщает службе о начале проверки, при нескольких исходящих пакетах без достаточного числа входящих переключает стратегию для текущего адреса, а после подтверждённого ответа сообщает победителя. Для Discord Voice отсутствие подтверждения в течение 15 секунд переводит канал в состояние ошибки; новый поток запускает проверку заново. Исторические версии движка не смешиваются: каждый комплект находится в отдельной папке со своими DLL, драйвером, Lua и blobs.

Обычные Debug- и Release-сборки подключают `RealZapretProcessManager`.
`FakeZapretProcessManager` используется только в явно запрошенном
демонстрационном режиме. Перед запуском реальный менеджер проверяет manifest и
SHA-256 всех исполняемых файлов и входов выбранной стратегии, запускает только
активную версию и помещает процессы в Job Object с флагом
`KILL_ON_JOB_CLOSE`. После остановки последнего процесса менеджер проверяет
зарегистрированный путь kernel-driver `WinDivert` и выгружает его только тогда,
когда путь совпадает с уже проверенным runtime KROT.

Служба имеет тип запуска `Manual`: GUI запускает её по требованию и отправляет
heartbeat через статусные запросы. При закрытии GUI служба получает `shutdown`;
если GUI завершился аварийно, отсутствие heartbeat останавливает runtime и саму
службу через 15 секунд.

## Состояния

Центральная state machine использует состояния:

```text
Off → Starting → TestingDirect → TestingSavedProfiles → Running → Stopping → Off
```

Сохранённый профиль для текущей сети запускается и проверяется первым. Прямой доступ и `SearchingProfiles` проверяются только при его отказе. Если проверка конкретного сервиса не проходит, для него всегда разрешён новый перебор до первой рабочей стратегии; профиль второго сервиса при этом сохраняется. Если каталог исчерпан, проблемный сервис остаётся красным. В состоянии `Running` служба раз в 90 секунд сначала проверяет наличие общего интернета, затем TCP-каналы. Изменение сетевых адаптеров, включая включение или выключение VPN и Wi-Fi, будит монитор немедленно; после двухсекундной стабилизации сети выполняется внеплановая проверка. При обрыве Wi-Fi счётчики отказов очищаются и подбор не запускается; после восстановления выдерживается короткая пауза. Повторный подбор начинается только после двух последовательных отказов конкретного сервиса при работающем интернете. Ошибки представлены состояниями `PartialFailure` и `FatalError`.

Служба возвращает по IPC отдельное состояние каждого канала. GUI опрашивает только локальный Named Pipe и отображает проверку, ожидание UDP-активности, рабочий прямой доступ, рабочий пресет или отказ независимо для каждого индикатора.

Во время активной сессии служба информационно отмечает маршрутизируемый VPN/TUN-адаптер или явно настроенный системный прокси. В GUI показывается «Работа через VPN/прокси», но этот статус не блокирует проверку и подбор стратегий. Клиенты вроде HAPP могут оставлять адаптер и маршрут включёнными даже при отключённом соединении в интерфейсе, поэтому сообщение описывает фактический сетевой маршрут, а не состояние кнопки стороннего клиента.

UI вычисляется из состояния и не хранит независимый набор конфликтующих флагов.

## Обновления

GUI проверяет публичный список GitHub Releases после открытия окна и затем раз
в сутки, пока приложение остаётся в трее. Учитываются только релизы с чистой
числовой версией (`1.0`, `1.1`, `2.0`); черновики и теги с текстовыми суффиксами
игнорируются. Приложение ничего не загружает автоматически:
при наличии более новой версии справа от основной кнопки появляется жёлтая
ссылка на страницу релиза с номером и кратким описанием.

Уведомление из трея повторяется не чаще одного раза в три дня для одной версии.
Версия и время последнего уведомления сохраняются в пользовательских настройках.
Недоступность GitHub не влияет на запуск и работу runtime; техническая ошибка
проверки попадает только в подробный журнал.

## Данные

- `%LocalAppData%\KROT zapret\settings.json` — пользовательские настройки;
- `%LocalAppData%\KROT zapret\logs\` — журнал GUI;
- `%ProgramData%\KROT zapret\service-state\logs\` — технический журнал службы;
- `%ProgramData%\KROT zapret\service-state\preset-cache.json` — победители TCP, QUIC и Voice по SHA-256-отпечатку сети;
- `%ProgramData%\KROT zapret\` — профили, списки, кэш и состояние службы;
- `Program Files\KROT zapret\` — только программные файлы.

Настройки сохраняются через временный файл, flush на диск и атомарную замену
с резервной копией. Размер читаемых настроек и кэша ограничен 1 MiB.
Каталог `service-state` доступен `SYSTEM` и администраторам на запись, а обычным
пользователям — только на чтение.

Обычные события жизненного цикла и ошибки записываются всегда. Галочка
подробного журнала немедленно включает в GUI и службе только технические
события: результаты проб, перебор стратегий и stdout runtime. Каждая из двух
областей логов хранит текущий файл и до четырёх архивов по 2 MiB, то есть не
более примерно 10 MiB на GUI и 10 MiB на службу. Отдельная запись также
ограничивается и очищается от управляющих переносов.
